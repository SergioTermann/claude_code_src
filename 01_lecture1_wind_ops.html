1. 项目背景：风电运维的特殊性

普通问答 Agent 的三大问题

  • 只会解释，不会闭环：能解释故障码，但不会拉运行曲线、查备件、生成工单
  • 知识不接地：没有机型、部件、现场环境和历史检修上下文
  • 安全不可控：可能跳过上锁挂牌、登塔许可、风速限制等强约束

风电场景的工业级要求

  • 时效性：告警后要快速判断继续观察、远程诊断、建议复位、限功率建议还是派工
  • 准确性：不能编造故障原因、备件型号、操作步骤
  • 可追溯：每个建议要能追到手册、SOP、历史工单或实时数据
  • 强合规：安全票、作业许可、风险点必须前置校验

项目目标

构建一个能处理“告警解释 + 故障定位 + 检修步骤推荐 + 备件/工具准备 + 工单闭环 + 复盘学习”的工业级风电运维智导 Agent。
关键定位：LLM 只能“告诉你可能怎么做”；运维 Agent 必须“拿实时数据、查规程、拆任务、形成建议、留下工单证据”。风电场景不能只做聊天助手，必须做可审计的人机协同作业辅助系统。

2.1 单体 Agent 反例 vs 风电分层架构

单体运维 Agent

agent = create_agent( llm=llm, tools=[cms, eam, weather, spare_parts, ticket, ...60+ tools], system_prompt="你是风电运维专家..." ) # 问题： # 1. 工具太多，模型容易选错 # 2. 安全规则被埋在 Prompt 里 # 3. 实时数据、知识库、工单逻辑互相耦合

七层风电运维架构

# 业务层：接收告警/人工提问 case = WindOpsBusiness.process(query, turbine_id) # 数据层：标准化故障实体和运行窗口 case = normalizer.enrich(case, operating_window, cms_signal) # 记忆层：取风机画像和类似故障 context = memory.search(turbine_id, fault_code, symptom) # 模型应用层：Planner 拆解诊断路径 plan = planner.plan(case, context, allowed_tools) # 工具层：按权限、安全票和重试策略调用系统 result = executor.run(plan)
风电改造重点：安全约束不能只放 Prompt，要在数据层和工具层做硬校验，例如风速、作业票、停机状态、控制类操作权限。助手默认只输出建议，控制系统执行必须走人工确认和既有权限链路。

3. 数据层 · 故障 Query 改写与实体对齐

为什么必须前置改写

  • 现场口语和厂家术语不一致：变桨 24V、pitch 24V、控制柜低压可能指向同一类问题
  • 风机编号、部件、告警码、时间窗缺一项，RAG 和工具调用都会漂移
  • 风况、功率、转速、温度、电压等实时状态决定诊断路径

三道兜底

  • 实体置信度低：先追问，不直接下结论
  • CMS/告警平台超时：使用最近缓存并标注数据时间
  • 危险操作：缺少作业票、风速超限、权限不足时强制阻断

3.2 画像动态更新：从用户行为改为工单闭环

不让 Agent 同步直写资产台账

  • 一次幻觉可能污染长期设备履历
  • 工单未验收前，故障原因只是候选结论
  • 实时链路不能被写库和审批拖慢

异步抽取 + 专家/工单确认

  • 实时层：当前告警和复位状态秒级更新
  • 批处理：工单关闭后更新长期画像
  • 置信度：专家确认、备件更换、复发情况共同加权

3.3 冷启动：新风场 / 新机型 / 新故障怎么办

① 台账 Onboarding

先导入风机台账、机型、部件 BOM、控制器版本、质保边界和安全规程。

最小可用画像来自 CMDB/EAM，而不是靠聊天慢慢积累。

② Look-alike 机群迁移

按机型、部件批次、地形风况、运行年限匹配相似风机群。

新风机没有历史，也能借鉴同批次同机型经验。

③ 专家规则兜底

对高风险故障优先用厂家手册、SOP 和专家审核路径。

新型故障不自动给确定结论，输出“排查路径 + 证据缺口”。

更新频率控制

  • 实时流：告警、限功率、停复机、复位结果，秒级进入工作记忆
  • 小时级批处理：关联多告警、抽取趋势特征、合并相似事件
  • 工单级沉淀：只有工单验收/专家确认后，才更新长期故障画像

4. Planner 子智能体 · 风电多步诊断为什么必须拆

单体 ReAct 的崩溃模式

  • 工具乱调：还没确认风机状态就给出复位或控制类建议
  • 漏安全检查：直接给登塔/开柜步骤，未校验风速、票证、停机状态
  • 诊断跳步：只凭故障码下结论，不看关联告警和曲线

Plan-and-Execute 改造

  • Planner：生成诊断路径，不直接执行危险操作
  • Safety Gate：每个步骤前校验权限和安全前置条件
  • Executor：严格按 plan 调工具，输出证据和下一步
Plan 示例： 1. 查询 WTG-003 近30分钟告警和停机状态 2. 拉取变桨 24V 电压、充电器状态、柜内温度曲线 3. 检索同机型“变桨24V低压”SOP 与历史工单 4. 判断是否满足“建议远程复位”的前置条件；不满足则生成现场排查清单 5. 检查备件库存：24V 电源模块、保险、端子、万用表 6. 生成工单草稿、证据清单和安全风险提示

4.2 Tool Calling：运维系统调用必须结构化

文本解析式 ReAct

Thought: 我需要查运行数据 Action: get_operating_data Action Input: 3号机 24V # 风险： # 文本稍有变化就解析失败 # 参数缺字段：风机ID、点位、时间窗 # 危险操作难以加权限拦截

结构化 Tool Calling

{ "tool_calls": [{ "name": "get_operating_timeseries", "arguments": { "turbine_id": "WTG-003", "points": ["pitch_24v_voltage", "pitch_charger_state"], "window": "last_30m" } }] }
工具类型示例关键约束
只读诊断工具CMS、历史告警、工单检索、运行数据必须带风机 ID、时间窗、数据时间戳
建议生成工具工单草稿、备件清单、排查清单输出为草稿，需人工确认
高风险控制类能力远程复位、启停机、参数调整不由助手直接执行；助手只生成建议和风险依据，执行走原控制系统权限、电子票和二次确认
风电场景的 Tool Calling 不只是“格式稳定”，更是“权限边界”。所有可能影响设备状态的能力必须从工具注册表中标记为高风险，默认禁用直连执行，只允许输出建议、校验项和审计记录。

4.3 Agent 框架：轻量可控，替代黑盒编排

直接套通用框架的问题

  • 工具链路太黑，现场事故复盘时难以解释每一步依据
  • 安全门、权限、票证、审计日志很难嵌入默认链路
  • 时序数据、知识库、工单系统混在一个 Agent 中，测试困难

自研最小可控内核

  • StateGraph：Case → Plan → Evidence → Recommendation → WorkOrder
  • ToolRegistry：所有工具声明权限、超时、降级策略
  • SafetyGate：风速、停机、票证、权限、二次确认
  • TraceLogger：每步证据、参数、模型输出全留痕
class WindOpsAgent: def run(case): case = data_layer.normalize(case) memory_ctx = memory_router.build(case) evidence = rag.retrieve(case, memory_ctx) plan = planner.plan(case, evidence) safe_plan = safety_gate.validate(plan) result = executor.execute(safe_plan) feedback.log(case, plan, result)

5. 混合 RAG · 单一向量检索不适合故障诊断

只用向量检索的问题

  • 故障码、点位名、备件号属于精确匹配，向量相似可能漏召回
  • 厂家手册、SOP、工单、图纸粒度不同，单一路径难以排序
  • 历史工单有噪声，不能和官方规程同等可信

三层漏斗改造

  • L1 语义缓存：高频故障问答、标准 SOP、常见告警解释
  • L2 混合召回：BM25 精确匹配 + 向量语义召回 + 图谱邻接
  • L3 Rerank + 证据分级：官方手册优先，历史工单作为补充
风电 RAG 的核心不是“找相似文本”，而是“找到可执行、可追溯、符合机型和安全条件的证据”。

7. 模型层 · 训推分离的风电模型路由

原课件的模型路由思想保留，但风电场景要把“简单 FAQ、复杂诊断、时序异常、多模态巡检、专家评分”拆开，不能所有请求都走一个大模型。
任务类型推荐模型/模块触发场景原因
标准 FAQ / 故障码解释小模型 + 语义缓存“303804 是什么故障”高频、低风险、低延迟
多步故障诊断强推理 LLM + Planner多告警、多系统、多部件关联需要拆任务和证据整合
时序异常识别专用时序模型 / 规则引擎电压波动、温度爬升、振动趋势数值趋势不应完全交给 LLM
巡检图片/视频多模态模型叶片裂纹、渗油、柜内烧蚀、端子松动图像证据进入诊断链
专家复核/Judge异步评审模型 + 专家规则工单关闭、答案抽检、知识入库进入反馈飞轮
训推一致性重点：故障标签体系、机型术语、SOP 版本、点位映射必须和线上一致；否则训练集学到的“变桨24V”到线上可能对应错点位。

8. 整体调用链路串讲

例子：值班员问“3号机变桨24V主电源开关怎么处理？”链路为：故障实体对齐 → 拉取 24V 电压/充电器/温度曲线 → 检索机型 SOP 和历史工单 → Planner 拆成远程确认、现场排查、安全校验、备件准备 → Executor 生成带证据的处置建议和工单草稿。

9. 试点收益指标：从商业转化改为运维效果

运维指标

MTTR 目标 -10%~20%
一次修复率目标 +5%~12%
重复故障率目标 -5%~10%

资产指标

可利用率目标 +0.1~0.3pp
非计划停机目标 -5%~10%
限功率时长目标 -3%~8%

工程指标

只读问答 P95 <2s
关键结论引用率 >90%
高风险直连执行 0 次

归因方式

  • MTTR 改善：Planner 拆诊断路径 + 工具辅助拉曲线 + SOP 直接命中
  • 一次修复率提升：风机画像 + 相似工单 + 备件清单减少现场往返
  • 重复故障率下降：工单复盘进入长期故障画像，识别根因而非只复位
  • 安全风险下降：Safety Gate 对高风险建议做前置校验，控制类执行仍走原权限系统
这些数字是试点目标，不是上线承诺。上线时要用分场站灰度或前后对照验证：同机型、同风况、同故障类型分组，避免把季节风况、备件供应、班组经验变化误认为助手收益。

11. 小结：三条主线

① 分层即可控

风电运维不能靠一个 Prompt 包打天下，要把实时数据、知识检索、工具执行、安全审计拆成独立层。

② 前置即准确

先把故障码、风机、部件、时间窗、风况和点位对齐，再让模型诊断，能显著降低幻觉。

③ 闭环即进化

工单结果、专家修正、复发情况先进入审核池和知识治理流程，通过质检后再进入记忆和训练集，智导助手才会越用越贴合场站。

最终形态：不是“风电知识问答机器人”，而是“有数据、有证据、有安全门、有工单闭环的运维决策辅助系统”。
